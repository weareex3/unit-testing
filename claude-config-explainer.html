Mental model: CLAUDE.md is the briefing doc (read every turn). Memory is the notebook (recalled when relevant). Settings/Hooks are the automation layer (run by the harness, not Claude). Skills are reusable macro programs you invoke on demand.
Key distinction: Claude reads vs harness executes

📖 Claude reads

  • CLAUDE.md — injected as system prompt context
  • Memory files — loaded when relevant
  • Skill definitions — prompt programs Claude follows

These shape Claude's reasoning and responses. You change behaviour by editing text.

⚙️ Harness executes

  • Hooks — shell commands triggered by events
  • Permissions — allow/deny tool calls before Claude sees them
  • Env vars — set in settings.json, passed to processes

These run outside Claude's reasoning. Memory/preferences cannot fulfil "always run X when Y" — only hooks can.

📄

CLAUDE.md

Persistent instructions baked into every conversation. Think of it as Claude's briefing document for a project or globally.
~/.claude/CLAUDE.md  ·  <project>/CLAUDE.md  ·  <subdir>/.claude/CLAUDE.md
Scope & loading order
🌍
Global — ~/.claude/CLAUDE.md

Loaded in every project. Put cross-project preferences, shell environment notes, your name/role, universal style rules.

📁
Project root — <repo>/CLAUDE.md

Loaded for that repo only. Architecture overview, tech stack, coding conventions, deploy commands, test commands.

📂
Sub-directory — <subdir>/.claude/CLAUDE.md

Loaded when Claude is working inside that folder. Module-specific rules, API contracts, local gotchas.

🤝
Imported — @path/to/other.md

Include another markdown file inline. Useful for shared team guidelines stored once and referenced everywhere.

What belongs in CLAUDE.md

✓ Good candidates

  • Coding style preferences (terse responses, no emojis)
  • Stack / framework notes ("this is Flask + SQLAlchemy")
  • Build, test, deploy commands
  • Architecture overview — where key modules live
  • Non-obvious constraints ("never mock the DB in tests")
  • Your role / experience level
  • Environment notes (OS, Python venv path, Node version)

✗ Don't put here

  • Ephemeral task details or in-progress work
  • Things already obvious from the code
  • "Always run X when Y" automation — use Hooks
  • Personal facts that change often — use Memory
  • Reusable multi-step task programs — use Skills
Example: Global CLAUDE.md
# Claude Code — Global Preferences

## Environment
- Windows 11 Pro, PowerShell primary shell (Bash also available)
- Projects live under `C:\Users\Me\Documents\`
- Python venv at `C:\Users\Me\Documents\myproject\venv`

## Preferences
- Terse responses — no trailing summaries, no "I've done X" narration
- No comments in code unless the WHY is non-obvious
- No emojis
- Prefer editing existing files over creating new ones
- Default model: Opus

## Deployment
- Railway CLI (`railway up`) for deployments
- Always run `python -m py_compile` on changed Python files before committing
Example: Project CLAUDE.md
# my-api — Project Notes

## Stack
- Python 3.12 / Flask / SQLAlchemy / PostgreSQL
- Frontend: React 18, Vite, Tailwind CSS

## Commands
- `flask run` — dev server (port 5000)
- `pytest` — unit + integration tests (hits real DB, no mocks)
- `railway up` — deploy to production

## Architecture
- `/api` — Flask blueprints, one per domain
- `/models` — SQLAlchemy models
- `/frontend/src` — React components

## Non-obvious rules
- Never use `.query` API — always use `db.session.execute(select(...))`
- All dates stored as UTC, displayed in Europe/London
Tip: Keep CLAUDE.md facts-only. If you find yourself writing "when Claude does X, it should also do Y" — that's a Hook, not a CLAUDE.md instruction.
⚡

Skills

Reusable prompt programs invoked as slash commands. Each skill is a markdown file with a system prompt Claude follows when you type /skill-name.
~/.claude/skills/  ·  <project>/.claude/skills/
What a skill is
📝
A markdown file = a slash command

Create .claude/skills/my-task.md → invoke with /my-task. The file contains the instructions Claude follows, tools it can call, and how to structure its output.

🔁
Reusable across sessions

Unlike typing instructions in chat (which disappear), skills persist. Great for recurring workflows: code review, scenario drafting, PR creation, security audits.

🎯
Can have trigger descriptions

Skills have a description field. Claude uses it to auto-suggest or auto-trigger the skill when your message matches the described intent — even without typing /.

📦
Can call tools

A skill can instruct Claude to use Bash, Read, Edit, WebSearch, MCP tools — anything available in the session. Think of it as an agent program.

Skill file anatomy
---
name: code-review
description: Review the current diff for bugs
  and simplification opportunities.
  Use when asked to review, audit, or
  check changed code.
args:
  - name: effort
    description: low/medium/high/max
    default: medium
---

# Instructions Claude follows when /code-review is invoked

You are a thorough code reviewer. Run `git diff` to
see what changed. Look for:

1. Correctness bugs — logic errors, off-by-ones, null
   dereferences, race conditions
2. Security issues — injection, unvalidated input
3. Simplification — duplicated logic, unnecessary
   abstractions

Report findings as a markdown list. Each finding:
- File and line number
- What the problem is
- Suggested fix

Effort level: {{effort}}
Good use cases for skills

🔍 Code review

Run a structured diff analysis with consistent output format every time.

📋 Scenario drafting

Turn a description of a business process into a structured test scenario — same format, every time.

🔒 Security audit

Systematic OWASP-style review of changed code on demand.

📊 Report generation

Pull data, format it, produce a Word/Excel/PDF in a repeatable way.

🚀 Deploy checklist

Run compile check → tests → Railway deploy as a single command.

🛠️ Init / setup

Bootstrap a new project with your exact conventions: folder structure, config, CLAUDE.md template.

Skill vs CLAUDE.md: If it's a standing rule ("always do X"), put it in CLAUDE.md. If it's a task you invoke on demand ("do this complex thing now"), make it a skill.

Memory

File-based persistent facts that carry across sessions. Claude reads them when relevant so you don't repeat yourself.
~/.claude/projects/<project-slug>/memory/
Four memory types
👤
user — who you are

Role, experience level, domain knowledge, communication preferences. Helps Claude pitch explanations at the right level.

💬
feedback — how to collaborate

Corrections and confirmations. "Don't mock the DB" or "single bundled PR was right here." Saves you repeating guidance. Includes WHY so Claude can judge edge cases.

📋
project — ongoing context

Who's doing what, why, by when. Merge freezes, compliance drivers, stakeholder constraints. Decays fast — keep updated.

🔗
reference — where to look

Pointers to external systems. "Pipeline bugs → Linear project INGEST." "Oncall dashboard → grafana.internal/d/api-latency."

Memory file format
---
name: feedback-no-db-mocks
description: Integration tests must hit a real
  database, not mocks
metadata:
  type: feedback
---

Never mock the database in tests.

**Why:** Prior incident where mock/prod
divergence masked a broken migration that
passed all tests but failed on deploy.

**How to apply:** Any test touching data
should use a real test DB, not a mock or
in-memory substitute. Flag if asked to mock.

# Memory Index

- [User role](user_role.md) — data scientist, observability focus
- [No DB mocks](feedback-no-db-mocks.md) — integration tests hit real DB
- [Merge freeze](project-merge-freeze.md) — freeze begins 2026-03-05

MEMORY.md is always loaded. Keep it under ~200 lines. Memory files are loaded on demand when relevant.
What NOT to save in memory

Code & architecture

File paths, function names, patterns — derivable by reading the repo. Stale the moment code changes.

Git history

Recent changes, who-changed-what — git log and git blame are authoritative.

Current-session tasks

In-progress work, step-by-step plans, temporary state. Use Tasks for those — they're session-scoped.

Memory vs CLAUDE.md: Memory stores facts about you and the project that accumulate over time. CLAUDE.md stores standing instructions for how Claude should behave. When in doubt: if it would make sense in a team README, put it in CLAUDE.md. If it's something you'd tell a new colleague about yourself or a recent decision, save it to memory.

Settings & Hooks

JSON config executed by the harness — not read by Claude. Permissions, env vars, automated shell commands on tool events.
~/.claude/settings.json  ·  <project>/.claude/settings.json  ·  settings.local.json
Settings files
🌍
~/.claude/settings.json

Global. Applies to all projects. Good for blanket permissions (npm, git read) and personal env vars.

📁
<project>/.claude/settings.json

Shared with the team (committed). Project-wide permissions, project hooks, shared env vars.

🔒
settings.local.json

Personal overrides for a project — gitignored. Personal API keys, local port overrides.

Permission rules
"permissions": {
  "allow": [
    "Bash(npm run *)",
    "Bash(git log:*)",
    "Bash(python -m py_compile *)",
    "Read(~/.ssh/*)"
  ],
  "deny": [
    "Bash(rm -rf *)",
    "Bash(git push --force*)"
  ]
}
Hooks — the automation layer
Hooks are the right answer when you want "from now on, whenever X, do Y automatically." Memory and CLAUDE.md cannot fulfil this — only hooks can. 
"hooks": {
  "PreToolUse": [{
    "matcher": "Bash",
    "hooks": [{
      "type": "command",
      "command": "echo 'Running bash: ' $TOOL_INPUT"
    }]
  }],
  "PostToolUse": [{
    "matcher": "Write|Edit",
    "hooks": [{
      "type": "command",
      "command": "python -m py_compile $TOOL_INPUT_PATH"
    }]
  }],
  "Stop": [{
    "hooks": [{
      "type": "command",
      "command": "notify-send 'Claude finished'"
    }]
  }]
}

Decision guide — "where should this go?"
🤔
"I want Claude to always write code a certain way"

→ CLAUDE.md (global for universal, project for repo-specific)

🤔
"I want to run the same complex task repeatedly with one command"

→ Skill — write the instructions once, invoke with /skill-name

🤔
"I told Claude something important last session and it forgot"

→ Memory — ask Claude to "remember" it, or use /consolidate-memory to clean up

🤔
"From now on, whenever Claude edits a file, run the linter"

→ Hook (PostToolUse on Write/Edit) — memory and CLAUDE.md cannot fulfil automation

🤔
"I'm tired of approving the same npm/git commands every time"

→ Permissions allowlist in settings.json — use /fewer-permission-prompts skill to auto-generate it

🤔
"I want /code-review one keypress away"

→ Keybinding in ~/.claude/keybindings.json
